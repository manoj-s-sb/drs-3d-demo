🟢 Persistence — how it sticks
  • Auto-save on every change: the operator tab subscribes to the store and writes the whole dataSource slice to localStorage("dataSourceConfig") whenever it changes (store.js). So each edit sticks even without pressing Save.
  • "Save & connect" button: also writes the whole slice ({...ds}) — nothing is dropped, including the new WebSocket fields.
  • On refresh: loadPersisted() rehydrates {...DEFAULTS, ...saved}, so every saved IP/port comes back. Only basePath is intentionally forced from code (no UI field for it).
  • Big-screen tab: reads localStorage on load but does not write it (operator-tab-only), so it can never clobber the operator's config with a stale copy. It uses the operator's absolute show URLs anyway.

Verdict: the Connection page is correct — each IP drives exactly the data it names, changes apply live, and updates persist across refresh.

Must-fix before production 2 remaining

B2 is fixed (see update log) and B4 was downgraded. The remaining blockers are B1 and B3.

🔴 Critical · B1

No React error boundary anywhere → one bad ball field = full white screen

The only error boundary in the codebase wraps the HDRI lighting (FixedScene.jsx EnvBoundary). If any live per-ball JSON has a shape that slips past the null-guards and throws during render (a NaN into CatmullRomCurve3, a malformed balls[0], an unexpected decisions structure), React unmounts the entire root → blank white big screen, recoverable only by reload. Suspense boundaries do not catch render errors.

Fix: wrap <ThreeScene>, the Canvas module subtree, and the ticker/overlay group in error boundaries that render null (keep the stadium / last-good frame) and log. A single bad ball then degrades one module instead of killing the broadcast.

🟢 B2 — FIXED (was Critical · wrong data on air)

Stump Map run numbers now come from the Score API, like the pitch map

The runs: 0 hardcode is gone. The bug had two layers, both fixed:

  • Operator never broadcast the per-ball score for stump shows. sendToBigScreen pushed the bowling analysis (which carries byBall) only for bowling/pitch modes, so the big screen had no runs to show. → Added stump to that branch (OperatorDashboard.jsx), so the over's per-ball runs/wickets are now loaded and sent.
  • Stump components never read byBall. → StumpMap.jsx now merges score.bowling.byBall into each dot's runs/wicket (dot colour + number), and StumpTicker.jsx's computeFigures reads it too (Runs / Economy / Maidens). Both fall back to the point's own values if the API is down — identical to MultiPitchMap.jsx.

Result on air: non-wicket dots show the real run number and correct colour (not grey "0"); the stump ticker shows real Runs / Economy / Maidens (not 0 / 0.00 / all-maidens). Wickets unchanged. loadStump still sets a 0 default only as the pre-merge fallback value.

🟠 High · B3

No HTTP timeout anywhere → an unreachable camera machine freezes Start / Send / live-poll

None of the axios.get/head calls (dataSource + score API) set a timeout; Axios default is infinite. If a configured machine is powered off / unplugged (black-holed IP, no TCP RST), each request hangs on the OS connect timeout (tens of seconds). The 3-second live-poll piles up hanging sockets; Start / Send-to-Big-Screen appears frozen mid-over. (A machine that actively refuses is fine — instant reset.)

Fix: add an explicit timeout (~1500 ms) to every dataSource and score-API axios call, or set axios.defaults.timeout.

🟢 B4 — NOT AN ISSUE (was flagged High; verified false)

Sample data cannot reach air when the operator is connected to the machine

Re-verified against the code. The big screen does not fetch cricket data using its own source setting — it plays the absolute URLs the operator resolved:

  • over / pitch / stump / single / DRS → all use cmd.urls / cmd.url / cmd.folderUrl (showCommands.js:397-475). In mission mode these are http://<machine-ip>/…, so the big screen fetches from the machine regardless of its own setting.
  • score / ticker → pushed to the big screen over cross-tab (sendBowlingAnalysis/sendSnapshot); the big screen never fetches score itself.
  • The big-screen tab also shares localStorage with the operator (same origin), so once the operator sets server mode the big-screen tab inherits it via loadPersisted(). An idle big screen fetches no cricket data at all.

Only theoretical leak — Swing, and only if ALL hold at once: (1) the big screen runs on a different browser profile/machine from the operator (doesn't share its localStorage), (2) that profile was never set to server mode, and (3) a Swing show is played. Swing is the one module that re-resolves via its own source (SwingAnalysis.jsx:97 → loadTrajectory); every other module is immune.

Status: not a blocker. Optional hardening to close even the Swing corner: send Swing as a resolved absolute URL (like the other modules) instead of {innings, over, ball} (~10 lines).

Lower-priority (safe to ship, worth a follow-up)

🔵 Medium

Silent failures the operator can't see

  • All balls 404 (machine offline for the over): no crash, no black — but nothing plays and no reason is shown. The missing count is computed yet only console.warn-ed. Surface it in the operator UI.
  • DRS calibration/asset load failure: DRS aborts cleanly (endDrs()) but silently — operator sees nothing happen. Add a toast.
  • Cued DRS video 404: the paused/cued branch attaches only loadeddata, not error — a 404 on a cued clip shows black on the cue until Play. The normal play path does handle errors + 30s safety fallback.
  • Big-screen command handlers (crossTabSync.js cueShow/playShow/executeCommand) aren't wrapped in try/catch; a malformed command could throw in the event handler.
🔵 Medium

Length-zone definitions are inconsistent (cosmetic classification drift)

Three different length-band boundary sets exist: LENGTH_ZONES (1/3/6/8 m, used for the bowling length label), PITCH_ZONE_MID_Z (pitch-map chip anchors), and PitchMapOverlay ZONES (2/6/8, used for the LENGTH DISTRIBUTION %). The same ball can be bucketed differently by each. Unify if the percentages must match the painted bands.

🔵 Medium

Pitch-map dot colours vs figures ticker can disagree

Pitch-map dot colours use the API-merged outcome, but the figures ticker (Runs/Economy) computes from the raw p.runs on the point (trajectory JSON). If API and JSON runs differ, the coloured dots and the numbers tell different stories.

The app has five live data sources plus hardcoded presentation config. 🟢 By design — not an issue
  • The 6 ball/chip colours are fixed on purpose. Ball 1 = red, 2 = blue, 3 = purple, 4 = green, 5 = brown, 6 = gold — every over, always. In bowling analysis the colour's job is just to tell the 6 trajectories apart, so it's positional, not outcome-based. (Outcome colours live in the pitch/stump maps.) Intended behaviour.
  • The camera is fixed in style, adaptive in aim — also by design. The angles, heights, lens (FOV), zoom push-in and timings are fixed presets so the look stays consistent and on-brand. But where the camera points/anchors is computed from where this over's balls actually are (their bounding box centre, bounce, release, stumps), so every over is well-framed regardless of line/length. Not a bug — this is how it was built.

🟢 By design — not an issue

The pitch map has two kinds of colour, and only one is (correctly) dynamic:

ColourWhatFixed / dynamic
Zone BAND coloursYorker = yellow, Full = green, Good = red, Short = purpleFixed — by design. These are the painted length zones (the pitch's "map"). They describe where each length is, so they must stay constant. No need to be dynamic.
DOT coloursdot = grey, 1–3 = green, four = blue, six = red, wicket = yellowDynamic — the actual deliveries, coloured by outcome (see rows above).
  • Zone bands + FULL/GOOD/SHORT labels are fixed on purpose. The band colours and their text (PITCHMAP_CONFIG, applied to the pitch_map.glb meshes by name) are the broadcast's fixed pitch layout — constant by design, not driven by match data. Correct as-is; they do not need to be dynamic.
  • Camera poses and dot sizes are fixed presets — also by design. The Hawk-Eye/top framing and the dot diameters live in pitchMapAnimations.js (with a separate set for the PiP window) so the look stays consistent. Because the pitch is always at the same spot in the scene, a fixed camera always frames it — no need to adapt (unlike Bowling Analysis). The dots (positions, run numbers, outcome colours) remain fully dynamic. Not a bug.
